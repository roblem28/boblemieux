# Accessibility Review (WCAG 2.1 AA)
_Method: rendered HTML from local prod build + compiled CSS + computed contrast ratios. No axe/browser run._

## Method note — why `curl` alone was not enough

`src/pages/_app.js:31` gates the whole app on a mount flag:

```jsx
{isMounted ? <Component {...pageProps} /> : null}
```

Every route therefore ships `<body><div id="__next"></div>` with **zero markup** — verified against both
`curl http://localhost:4321/` and the on-disk prerender `.next/server/pages/index.html`. All content is
produced client-side after hydration.

To audit real markup I bundled the actual page/section source with esbuild (aliasing `next/dynamic` to a
synchronous loader) and server-rendered each route from the `__NEXT_DATA__` pageProps captured from the
running server. That produced true DOM for all 27 content routes. The five hand-written pages under
`public/` were fetched directly. Contrast ratios were computed with a WCAG relative-luminance script
(node, plus PowerShell + `System.Drawing` for per-pixel analysis of the background photographs).

## Findings

### [P1] `<html>` has no `lang` attribute on any route
- **Where:** no `src/pages/_document.*` exists; `next.config.js` sets no `i18n`. Verified: `<html>` in `.next/server/pages/index.html` and in every `curl` response, and the client cannot add it post-hydration.
- **Problem:** Every page of the site ships `<html>` with no language. Screen readers fall back to the user's system voice and pronunciation rules for all content.
- **WCAG:** 3.1.1 Language of Page (Level A)
- **Fix:** Add `src/pages/_document.tsx` with `<Html lang="en">`.
- **Confidence:** high

### [P1] Body text over `/images/marley1.jpg` drops to 1.86:1
- **Where:** `content/pages/projects/marley1.md:5-11` (`backgroundImage: /images/marley1.jpg`, `opacity: 75`) rendered by `src/components/atoms/BackgroundImage/index.tsx`; route `/projects/marley1`.
- **Problem:** `BackgroundImage` paints a `fixed inset-0` photo at 75% opacity, and every section on the page is `data-theme="colors-f"` (transparent), so the near-white body copy sits directly on the photograph. Per-pixel analysis (150×100 sample, composited 75% over `#000`): **worst 1.86:1, 5th percentile 1.92:1, median 5.79:1; 43.4% of the frame below 4.5:1 and 21.8% below 3:1.**
- **WCAG:** 1.4.3 Contrast (Minimum) (AA)
- **Fix:** Lower `opacity` to ~30–40%, add a scrim (`bg-main/70`) between the image and `<main>`, or give the text sections an opaque `colors-a` background instead of `colors-f`. The site-wide default `bg1.jpg` at the same 75% is safe (worst 5.85:1), so this is specific to the brighter `marley1.jpg`.
- **Confidence:** high

### [P1] Contact-form placeholder text fails contrast (2.52:1 worst, 71.5% of the area)
- **Where:** `src/components/molecules/FormBlock/TextFormControl/index.tsx:29`, `TextareaFormControl/index.tsx:29`, `EmailFormControl/index.tsx:29`, `SelectFormControl/index.tsx:26` — all carry `placeholder:text-current placeholder:opacity-50`. Rendered on `/` ("Got an interesting project?") and `/info` ("Get in touch").
- **Problem:** `opacity-50` on `#FBFFF2` composited over `/images/bg1.jpg` @75% gives **worst 2.52:1, median 3.97:1**, with 71.5% of the background area below 4.5:1. Against flat black it would be 5.25:1 — the photo background is what pushes it under.
- **WCAG:** 1.4.3 (AA)
- **Fix:** Raise to `placeholder:opacity-80` (5.19:1 on the darkest palette, and comfortably above threshold over bg1), or drop the opacity modifier entirely once the labels problem below is fixed.
- **Confidence:** high

### [P1] Placeholder text is the only visible label on every contact-form field
- **Where:** `src/components/molecules/FormBlock/*FormControl/index.tsx` — `hideLabel` is set for all five fields, so every `<label>` renders with `sr-only`. Rendered markup on `/`:
  `<label id="firstName-label" class="… sr-only" for="firstName">First Name</label>` followed by `<input … placeholder="First Name">`
- **Problem:** Sighted users (including users with cognitive disabilities, and anyone who has started typing) lose the field name entirely once a value is entered. The programmatic label is fine; the visible one disappears.
- **WCAG:** 3.3.2 Labels or Instructions (Level A)
- **Fix:** Set `hideLabel: false` in the form content, or render a persistent floating label.
- **Confidence:** high

### [P1] Mobile menu open/close buttons have no visible focus indicator
- **Where:** `src/components/sections/Header/index.tsx:132` and `:144` — both `<button>` elements carry `focus:outline-hidden` with no replacement. Compiled CSS confirms: `.focus\:outline-hidden:focus{--tw-outline-style:none;outline-style:none}` (the only fallback is a transparent 2px outline inside `@media (forced-colors:active)`).
- **Problem:** On narrow viewports these two buttons are the only route to site navigation, and a keyboard user gets no indication at all when they are focused.
- **WCAG:** 2.4.7 Focus Visible (AA)
- **Fix:** Replace with `focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-current`, or simply delete `focus:outline-hidden` and let the UA ring show.
- **Confidence:** high

### [P1] Consent checkbox is invisible when focused
- **Where:** `src/components/molecules/FormBlock/CheckboxFormControl/index.tsx:17`
  `className="absolute w-[1.5em] h-[1.5em] opacity-0 appearance-none select-none peer"`
- **Problem:** The real `<input type="checkbox">` is `opacity-0`; the visible box is the label's `::before` pseudo-element, which has no `peer-focus` / `peer-focus-visible` styling. A keyboard user tabbing through the form loses their position completely at this control — nothing on screen changes when it receives focus.
- **WCAG:** 2.4.7 Focus Visible (AA)
- **Fix:** Add `peer-focus-visible:before:outline peer-focus-visible:before:outline-2 peer-focus-visible:before:outline-offset-2` to the label's class list.
- **Confidence:** high

### [P1] Skip link never becomes visible
- **Where:** `src/components/sections/Header/index.tsx:23`
  `<Link href="#main" className="sr-only">Skip to main content</Link>`
- **Problem:** `.sr-only` clips it to 1×1px permanently — there is no `focus:not-sr-only`. Screen-reader users can reach it, but sighted keyboard users get an invisible first tab stop and no working skip mechanism. The target (`<main id="main">`, `BaseLayout/index.tsx:29`) is correct.
- **WCAG:** 2.4.7 Focus Visible (AA); undermines 2.4.1 Bypass Blocks
- **Fix:** `className="sr-only focus:not-sr-only focus:absolute focus:z-50 focus:p-4 focus:bg-main"`.
- **Confidence:** high

### [P1] Mobile menu has no dialog semantics, no state exposure, no focus management, no Escape
- **Where:** `src/components/sections/Header/index.tsx:118-165` (`MobileMenu`).
- **Problem:** Four separate gaps on the same control:
  1. The `aria-label="Open Menu"` button has **no `aria-expanded` and no `aria-controls`** — the open/closed state is invisible to assistive tech.
  2. The overlay is a plain `<div className="fixed inset-0 z-20 … bg-main">` with **no `role="dialog"` / `aria-modal="true"`**.
  3. Opening it does **not move focus** into the panel, and there is no focus trap — tabbing past the last menu link lands on page content that is completely obscured by the overlay.
  4. There is **no Escape handler**; the only close paths are the close button and a route change (`useEffect` on `routeChangeStart`).

  What it does get right: the panel is `hidden` (i.e. `display:none`) when closed, so its links are correctly **not** reachable by keyboard.
- **WCAG:** 4.1.2 Name, Role, Value (A); 2.4.3 Focus Order (A)
- **Fix:** Add `aria-expanded={isMenuOpen} aria-controls="mobile-menu"` to the toggle, give the overlay `id="mobile-menu" role="dialog" aria-modal="true"`, move focus to the close button on open and restore it on close, trap Tab inside the panel, and close on Escape.
- **Confidence:** high

### [P1] Home page has two `<h1>` elements
- **Where:** `src/components/sections/HeroSection/index.tsx:26` hardcodes `<h1>`; `content/pages/index.md` uses two `HeroSection` blocks. Rendered outline on `/`: `h1 "Digital Leverage"` … `h1 "Project Leadership"`.
- **Problem:** Two competing top-level headings; screen-reader users navigating by heading get an ambiguous page structure.
- **WCAG:** 1.3.1 Info and Relationships (A)
- **Fix:** Give `HeroSection` a `headingLevel` prop the way `FeaturedItemsSection` already does for its items (`FeaturedItemsSection/index.tsx:47` passes `headingLevel={title ? 'h3' : 'h2'}` to `FeaturedItem`), and set the second hero to `h2`.
- **Confidence:** high

### [P1] `/projects/fec`, `/projects/nyt`, `/projects/spending` have no headings at all
- **Where:** `src/pages/projects/fec.tsx:22-29`, `nyt.tsx:30-41`, `spending.tsx:20-28` — each renders `<BaseLayout>` wrapping only an `<iframe>`.
- **Problem:** The page has a `<main>` and a `<title>`, but no `h1` and no in-page text. A screen-reader user landing here, or navigating by heading, has nothing to orient on before being dropped into a cross-document iframe.
- **WCAG:** 1.3.1 (A); 2.4.6 Headings and Labels (AA)
- **Fix:** Add a visible `<h1>` above each iframe naming the tool (the `<title>` text already exists, e.g. "FEC Campaign Finance Explorer"). Credit where due: all three iframes **do** carry a correct `title` attribute (`fec.tsx:25`, `nyt.tsx:36`, `spending.tsx:24`), as does the mindmap embed on `/`.
- **Confidence:** high

### [P1] 3D mind-map widget is inaccessible non-visually and by keyboard
- **Where:** `public/widgets/mindmap-3d.html` — `<canvas id="c"></canvas>` plus a `pointer-events:none` HUD. Embedded on `/` in the "Active Work — 3D Map" section.
- **Problem:** The entire information payload (dozens of project node names, held in the page's `DATA` object) is rendered only into a WebGL canvas. There is no `role="img"` / `aria-label`, no fallback content, and no text equivalent. The stated interactions — "drag rotate · pinch/scroll zoom · tap node to focus" — are pointer-only; there is no keyboard path to focus a node.
- **WCAG:** 1.1.1 Non-text Content (A); 2.1.1 Keyboard (A)
- **Fix:** Render `DATA` as a visually-hidden nested `<ul>` inside the canvas fallback (it is already a tree), and add `role="img"` plus a summarising `aria-label` to the canvas. Keyboard node-focus is a larger change; the text equivalent alone removes the blocker.
- **Confidence:** high

### [P1] `/wire/` conveys all structure through styling — zero headings, zero landmarks
- **Where:** `public/wire/index.html`
  `<div class="masthead">THE AI WIRE</div>` · `<div class="tagline">…</div>` · `<div class="colhead">MONEY &amp; MACHINES</div>` (×3)
- **Problem:** A three-column news page with a masthead and three section heads, none of which is a heading element. No `<main>`, no `<nav>`, no `<h1>`. Heading navigation and landmark navigation are both unavailable; the page reads as one undifferentiated list of links. (Contrast and link underlining on this page are fine — `.siren` `#c00` on white is 5.89:1, visited links `#444` are 9.74:1.)
- **WCAG:** 1.3.1 (A)
- **Fix:** `masthead` becomes `<h1>`, each `colhead` becomes `<h2>`, wrap `.cols` in `<main>`. Purely additive; the Drudge-style visual design is unaffected. (This page must be preserved — the fix is markup-only.)
- **Confidence:** high

### [P2] 81 links carry `aria-label=""`
- **Where:** `content/data/config.json` — footer `primaryLinks` for Info, Contact and Blog each set `"altText": ""`; `src/components/atoms/Action/index.tsx:39` passes it straight through as `aria-label={altText}`. Renders three times on each of the 27 routes.
  `<a href="/info" aria-label="" class="…">Info</a>`
- **Problem:** Not a name-computation failure in practice — per the accname spec an empty or whitespace `aria-label` is skipped and the link falls back to its text content, so these links are still announced as "Info", "Contact", "Blog". It is nonetheless invalid ARIA that trips automated scanners and is one content edit away from being a real bug.
- **WCAG:** 4.1.2 (A) — advisory
- **Fix:** Remove the three `"altText": ""` entries, or guard with `aria-label={altText || undefined}` in `Action`.
- **Confidence:** high

### [P2] Every inline SVG icon is unmarked (260 instances)
- **Where:** all 26 files in `src/components/svgs/*.tsx`; e.g. `menu.tsx:5` `<svg className={className} viewBox="0 0 24 24" xmlns="…">`.
- **Problem:** No `aria-hidden`, `role`, `focusable`, or `<title>` anywhere. All are decorative — the containing `<button>` / `<a>` supplies the name (Header buttons via `aria-label`, `Social` via `aria-label` plus an `sr-only` span) — so the correct marking is `aria-hidden="true" focusable="false"`. Without it some AT announce a bare "graphic" and legacy engines put the SVG in the tab order.
- **WCAG:** 1.1.1 (A) — advisory
- **Fix:** Add `aria-hidden="true" focusable="false"` to the `<svg>` in each component.
- **Confidence:** high

### [P2] Header and footer link lists are not `<nav>` landmarks
- **Where:** `src/components/sections/Header/index.tsx:48,54,70,80,92,98` (bare `<ul>`); `src/components/sections/Footer/index.tsx` (footer `<ul>`, seen in rendered output). Confirmed: `nav=0` on all list/index routes; the only `<nav>` in the whole site is the prev/next pair in `ProjectLayout/index.tsx:65`.
- **Problem:** Landmark navigation cannot reach the primary or footer navigation. `<header>`, `<main>` and `<footer>` are all present and correct.
- **WCAG:** 1.3.1 (A) — advisory
- **Fix:** Wrap the primary-links `<ul>` in `<nav aria-label="Primary">` and the footer `<ul>` in `<nav aria-label="Footer">`. Add `aria-label="Project navigation"` to the existing `ProjectLayout` `<nav>`.
- **Confidence:** high

### [P2] Form-field focus indicator is a 1px ring adjacent to an identical 1px border
- **Where:** `TextFormControl/index.tsx:29` and siblings: `border border-current … focus:outline-none focus:ring-1 focus:ring-current`. Compiled CSS confirms the ring is generated: `.focus\:ring-1:focus{--tw-ring-shadow:… 0 0 0 calc(1px + …) var(--tw-ring-color,currentColor)}` with `.focus\:ring-current:focus{--tw-ring-color:currentColor}`.
- **Problem:** Focus replaces the UA outline with a 1px ring in the *same colour* immediately outside a 1px border of that colour — visually the border just gets 1px thicker. Technically visible; practically very easy to miss.
- **WCAG:** 2.4.7 (AA), borderline; fails 2.4.11 Focus Appearance (AAA)
- **Fix:** `focus-visible:ring-2 focus-visible:ring-offset-2` (offset in the section background colour), and drop `focus:outline-none`.
- **Confidence:** med

### [P2] Redundant `aria-labelledby` on every form control

- **Problem:** The native `for` / `id` association already names the control; the `aria-labelledby` duplicates it and silently overrides it, so a future divergence between the two would be invisible.
- **WCAG:** 4.1.2 (A) — advisory

- **Where:** `grep -c prefers-reduced-motion .next/static/css/*.css` returns **0** in both compiled stylesheets; `src/css/main.css` has none either.
- **Problem:** Motion in the app is limited to hover-triggered transitions (`hover:-translate-y-1.5` on buttons in `Action/index.tsx:30`, `group-hover:scale-105 duration-500` on project-nav images) plus two MapLibre spinner keyframes. These are user-initiated, so this is a polish item rather than an SC failure — but the block costs nothing. Note the hand-written pages already do this: the comic and Cheeseburgler both ship `@media (prefers-reduced-motion: reduce)`.
- **WCAG:** 2.3.3 Animation from Interactions (AAA) — advisory at AA
- **Fix:** Add a global reduced-motion block to `main.css` neutralising `transition` / `animation`.
- **Confidence:** high

### [P2] `/404` renders Next's built-in error page with no site chrome
- **Where:** no `content/pages/404.*` and no `src/pages/404.tsx`; `.next/server/pages/404.html` body is `<div id="__next"></div>` with `pageProps: {statusCode}`.
- **Problem:** A user who hits a bad URL gets the framework default — no header, no `<main>`, no navigation back into the site, and (like every route) no `lang`.
- **WCAG:** 2.4.1 Bypass Blocks / 1.3.1 — advisory
- **Fix:** Add a custom 404 page that renders inside `BaseLayout`.
- **Confidence:** high

### [P2] Nothing is server-rendered before hydration
- **Where:** `src/pages/_app.js:31` — `{isMounted ? <Component {...pageProps} /> : null}`.
- **Problem:** Primarily an SEO/performance issue (and likely covered by another reviewer), but it has two accessibility consequences: it is the reason `lang` can never be set from a custom `_document` alone without also fixing the gate, and any assistive technology or proxy that consumes the document without executing JS receives a completely empty page. `<title>` is injected by `next/head` after hydration, so 2.4.2 Page Titled is met once JS runs — all 27 route titles are present and unique.
- **WCAG:** — (robustness; enables the 3.1.1 failure above)
- **Fix:** Remove the `isMounted` gate; the components render fine on the server (verified — this review's markup was produced by SSR-ing them directly).
- **Confidence:** high
